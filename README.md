# 금융인증서 발급·검증 인프라 보안 설계

은행 금융인증서 서비스의 발급·검증 인프라를 설계하고, 단계별 위협을 OWASP Top 10 기준으로 분석했다. 설계 프로젝트이며 구축은 하지 않았다.

| 내 역할 | 자료조사, 서버 구성 설계, 네트워크 구성 설계 |
| 범위 | PKI, CRL, OCSP 기반 인증서 발급·검증 흐름과 보안 통제 |

## 1. 목표

- 금융인증서 발급·검증 구조와 서버·네트워크·PKI 기반 아키텍처 이해
- 실제 금융 서비스 수준의 인프라 설계
- 위협 모델링과 OWASP 기반 공격 시나리오 도출
- 위협에 대응하는 보안 정책 설계

## 3. 아키텍처

초기에는 인증서 발급·검증 흐름에 필요한 최소 서버와 네트워크 구간만 구성했고, 이후 보안성·가용성·확장성을 보강해 최종 구조로 발전시켰다.

```
Public  -> DMZ (10.10.10.0/24):   WEB Server (WAF + Load Balancer) -> API Gateway
        -> APP (10.10.20.0/24):   Auth WAS, Cert WAS, Core WAS
                                   인증 채널: SMS / ARS / OTP
                                   인증서 채널: PKI·CA, CRL, OCSP
        -> DATA (10.10.30.0/24):  Cert DB, User DB, Log DB

ADMIN (10.10.50.0/24): 관리자 PC -> VPN + MFA -> SSH -> Bastion
                       -> Reverse Proxy, Auth/Cert WAS, DB Server, SIEM
```

| 구역 | 역할 |
|---|---|
| Public | 외부 인터넷 |
| DMZ | 완충 구간, IP 은닉 |
| APP | 비즈니스 로직, 인증 |
| DATA | 핵심 자산, 최상위 보안 |
| ADMIN | 관리자 전용 |

**요청 흐름**
1. WAF에서 1차 필터링
2. API Gateway에서 토큰 검증
3. App Zone에서 업무 로직 수행
4. DB Zone은 App Zone에서만 진입
5. Audit Log는 Append-Only

Public → DMZ → Application → Data의 단방향 진입 구조이고, 구역 경계는 방화벽으로 통제한다. 침해가 발생해도 피해를 국소화하는 것이 목적이다.

## 4. 관리자 접근 통제

관리자 PC와 Bastion Server로 관리자 경로를 일반 사용자 트래픽과 분리했다. 관리자는 외부에서 내부 서버로 직접 접근할 수 없고, 승인된 경로(VPN, MFA, Bastion)로만 관리 작업을 한다.

| 통제 대상 | 정책 |
|---|---|
| 서버 원격 접속 | 직접 SSH 금지, Bastion 경유만 허용 |
| 관리자 인증 | MFA 필수, SSH Key 기반 |
| 접속 기록 | 모든 접속·명령 실행을 Audit Log에 저장 |
| 관리자 웹 페이지 | 관리자 전용망 또는 VDI/Admin PC에서만 접근 |
| 권한 분리 | 업무별 RBAC (고객 조회 / 발급 승인 / 감사 로그 열람 분리) |
| 민감 기능 | 인증서 발급 승인·폐기 시 MFA 재인증 |
| DB 접근 | 업무상 필요한 최소 권한, WAS 또는 승인된 관리자 계정만 접근 |
| 이상 행위 | 대량 조회·비정상 쿼리 발생 시 대응·경보 |

## 5. 사용자 인증

| 항목 | 내용 |
|---|---|
| 사용자 식별 | 가입 시 실명과 본인 계좌 정보 검증 (이름, 계좌번호, 예금주 일치 확인) |
| 사전 검증 | 인증 전 계정 상태, 인증서 상태, 실패 횟수(Fail Count) 확인. 비정상 상태 계정의 PIN 인증 차단 |
| 시도 제한 | 5회 실패 시 10분 잠금, 10회 이상은 관리자 해제 필요. 동일 IP·계정 기준 Rate Limiting |
| 오류 응답 | 일반화된 메시지로 상세 정보 비노출 |
| 인증 수단 | SMS, ARS, OTP. 인증번호는 제한 시간 내에만 유효 |
| 토큰 | OAuth 2.0 + JWT. ID/PW 검증 후 Access Token(10분)과 Refresh Token 이원화 발급, 만료 시 자동 갱신 |
| 추가 인증 | 금융인증서 발급·검증, 개인정보 변경 시 MFA |

## 6. 데이터 보호

| 구간 | 정책 |
|---|---|
| 외부 사용자 ↔ Web Server | SSL/TLS 기반 HTTPS |
| Web → API Gateway → WAS | 내부 사설 mTLS |
| 저장 (DB) | 거래 이력, Audit Log, DB 파일에 TDE. 데이터 파일, 테이블스페이스, 백업 파일을 엔진 수준에서 암호화 |
| 키 관리 | KMS/HSM 분리 보관, 키 접근 승인 기반 최소 권한, 6~12개월 주기 Rotation |

전송 구간의 도청·위변조·MITM을 막고, 저장 매체 탈취나 백업 유출 시에도 원문이 보호되도록 했다.

## 7. 로그

| 항목 | 내용 |
|---|---|
| 기록 대상 | 관리자 접속, 서버 접근, 시스템 에러, ARS·SMS·OTP 인증, 전자서명, 인증 실패, 로그인/로그아웃(사용자 ID, IP, 접속 시간), 전자금융 거래, 개인정보 접근 |
| 저장 | 모든 로그를 중앙 Audit Log 서버에 Append-Only로 저장 |
| 보관 | 로그 종류에 따라 1년 이상 ~ 5년 |
| 점검 | 일일(관리자 접근, 이상 인증 시도, 침입 탐지), 주간, 월간(권한 변경, KMS 키 접근, 복구 훈련) |

## 8. 인증서 흐름

**발급 시퀀스**
1. 금융인증서 발급 및 본인인증 요청
2. 5회 누적 실패 여부 사전 체크
3. 본인 인증 (ARS / SMS / OTP)
4. 인증 결과 반환 및 금융인증서 발급

**검증 시퀀스**
1. 금융인증서 검증 및 접근 요청
2. 5회 누적 실패 여부 사전 체크
3. 금융인증서 유효성 체크
4. 비밀번호 및 서명값 검증
5. 검증 결과 확인 및 금융 서비스 접근

## 9. 위협 분석 (OWASP Top 10)

시퀀스의 단계(번호)마다 가장 치명적인 위협을 매핑했다.

**발급**

| OWASP | 시퀀스 단계 | 위협 예시 | 대응 |
|---|---|---|---|
| A01 | [3] API 호출 | API 인증 검증 미흡으로 인증 우회 | API 인증 및 권한 검증 |
| A03 | [30] OTP 번호 검증 시도 | 취약한 OTP 모듈 사용으로 서버 침해 | 보안 패치 및 버전 관리 |
| A08 | [44] 인증서 생성 요청 | 위조 인증서 발급 | CSR 서명 검증 |
| A09 | [48] 발급 이력 Audit Log 기록 | 공격 흔적 삭제 | Append-Only 저장 |

**검증**

| OWASP | 시퀀스 단계 | 위협 예시 | 대응 |
|---|---|---|---|
| A01 | [38] 처리 결과 전달 (200 OK) | 응답값 변조, 권한 우회 | 서버 세션 인가 검증 |
| A04 | [12] 인증서 상태 검증 요청 | 위조·만료 인증서 신뢰 | Chain of Trust 검증 |
| A07 | [22] 비밀번호·서명값 검증 요청 | 인증 패킷 재사용 | 일회성 난수 기반 검증 |
| A09 | [20] Audit Log 적재 | 로그 내 인증정보 평문 노출 | 민감정보 마스킹, 해시 처리 |

## 10. 어려웠던 점

- 주제가 OTP로 정해졌는데 웹 환경에서 지원되지 않는 부분이 있어 방향 설정에 어려움이 있었다.
- 팀 모두 금융 도메인과 인프라 구조가 처음이라 용어 정리와 구조 이해에 시간이 걸렸다.

## 11. 사용 기술·개념

PKI, CRL/OCSP, WAF, API Gateway, Bastion, VPN, MFA/RBAC, OAuth 2.0/JWT, TLS/mTLS, TDE, KMS/HSM, SIEM, OWASP Top 10
